## Part 1: App Configs Omarchy Provides That You're Missing

### How Omarchy Manages Configs

Omarchy has a two-part config system:

1. **Default configs** in `~/.local/share/omarchy/config/` -- copied to
   `~/.config/` via `omarchy-refresh-<app>` commands (one-time bootstrap,
   user edits preserved afterward).
2. **Theme fragments** in `~/.config/omarchy/current/theme/` -- regenerated
   on every theme switch from `.tpl` templates + `colors.toml`.

Apps `import`/`source`/`include` the theme fragments, so theme switching is
non-destructive to user configs.

## Part 3: Theming Strategy

### Current State: Three Layers, No Coordination

The system has three independent theming systems:

```
Layer 1: Omarchy (runtime, Linux only)
  Engine:  sed templates + colors.toml
  Palette: Catppuccin Mocha (#1e1e2e bg, #89b4fa accent)
  Manages: terminals, waybar, walker, mako, btop, hyprland colors,
           hyprlock, neovim, vscode, obsidian, chromium
  Switch:  `omarchy-theme-set tokyo-night` (instant, live)

Layer 2: Matugen / Material You (runtime, Linux only)
  Engine:  Material Design color extraction from wallpaper
  Palette: Generated from current wallpaper (varies)
  Manages: Hyprland borders/bars, GTK 3/4, QuickShell, fuzzel
  Switch:  automatic on wallpaper change

Layer 3: Chezmoi (build-time, cross-platform)
  Engine:  Go templates at `chezmoi apply` time
  Palette: Catppuccin Mocha (hardcoded in tmux, zellij, fish plugin)
  Manages: tmux, zellij, fish shell colors
  Switch:  edit config + `chezmoi apply`
```

**Problems with the status quo:**

- Layers 1 and 3 both use Catppuccin Mocha but don't share a definition.
- Layer 2 generates different colors than Layers 1/3.
- Switching omarchy theme to `tokyo-night` leaves tmux/zellij on Catppuccin.
- macOS has no runtime theming at all (Layer 3 only).
- No single place answers "what theme am I using?"

### Strategy Options

#### Option A: Accept the Split (Minimal Change)

Keep things as they are. Add configs to chezmoi without adding any theming
infrastructure.

- **On Linux**: Omarchy owns runtime theming for desktop apps. Chezmoi
  manages the config structure but not colors. tmux/zellij stay hardcoded
  Catppuccin.
- **On macOS**: Hardcoded Catppuccin in terminal tools. No desktop theming.
- **Pros**: Simple, no new systems to build.
- **Cons**: Theme switching on Linux doesn't affect tmux/zellij. macOS
  can't switch themes without editing configs.

#### Option B: Chezmoi Theme Data Layer (Build-Time Unification)

Add a `.chezmoidata/theme.yaml` defining the base theme. Chezmoi templates
render it into configs at apply time.

```yaml
# .chezmoidata/theme.yaml
theme:
  name: catppuccin-mocha

  # Tool-specific theme identifiers (for tools with built-in theme systems)
  tmux_flavor: mocha           # @catppuccin_flavor value
  zellij_theme: catppuccin-mocha
  bat_theme: catppuccin-mocha
  fish_plugin: catppuccin      # Fisher plugin name

  # Raw colors (for tools that need explicit color values)
  colors:
    background: "#1e1e2e"
    foreground: "#cdd6f4"
    accent: "#89b4fa"
    cursor: "#f5e0dc"
    selection_bg: "#585b70"
    selection_fg: "#cdd6f4"
    black: "#45475a"
    red: "#f38ba8"
    green: "#a6e3a1"
    yellow: "#f9e2af"
    blue: "#89b4fa"
    magenta: "#f5c2e7"
    cyan: "#94e2d5"
    white: "#bac2de"
```

**How it works:**

- `tmux.conf.tmpl`: `@catppuccin_flavor "{{ .theme.tmux_flavor }}"`
- `kitty.conf.tmpl` on macOS: render `{{ .theme.colors.background }}` etc.
- `kitty.conf.tmpl` on Linux: `include ~/.config/omarchy/current/theme/kitty.conf`
  (omarchy overrides at runtime)
- `ghostty/config.tmpl` on macOS: render colors from theme.yaml
- `ghostty/config.tmpl` on Linux: omarchy theme file import (if enabled)

**Theme switching:**

- Linux: `omarchy-theme-set <name>` for desktop apps (instant). To update
  tmux/zellij, also edit `theme.yaml` + `chezmoi apply`.
- macOS: Edit `theme.yaml` + `chezmoi apply` (updates everything).

**Pros**: Single source of truth for base theme. Cross-platform. Uses
existing `.chezmoidata/` patterns.

**Cons**: Two-step theme switch on Linux (omarchy + chezmoi). Build-time,
not runtime.

#### Option C: Omarchy Hook Bridge (Runtime on Linux, Build-Time on macOS)

Like Option B, but add an omarchy `theme-set` hook that auto-updates
chezmoi's theme data when you switch themes on Linux.

```bash
# ~/.config/omarchy/hooks/theme-set
#!/bin/bash
# After omarchy switches theme, update chezmoi and re-apply
THEME_NAME=$(cat ~/.config/omarchy/current/theme.name)
# Map omarchy theme name -> chezmoi theme.yaml values
# Run chezmoi apply to update tmux/zellij/fish
```

**Pros**: Single action (`omarchy-theme-set`) updates everything including
tmux/zellij.

**Cons**: Adds complexity. Hook needs to map omarchy theme names to
tmux/zellij theme names. `chezmoi apply` during theme switch may be slow.

#### Option D: Dedicated Theme Manager (New Tool)

Build a standalone theme-switching script that coordinates all layers:

```bash
# dotfiles-theme set catppuccin-mocha
# 1. Updates .chezmoidata/theme.yaml
# 2. Runs chezmoi apply (updates tmux, zellij, fish)
# 3. On Linux: runs omarchy-theme-set (updates desktop apps)
# 4. On macOS: directly updates terminal app configs
```

**Pros**: Unified interface. One command, everything changes.

**Cons**: New tool to maintain. Coupling between chezmoi and omarchy.

### Recommendation

**Option B** (Chezmoi Theme Data Layer) is the recommended starting point:

1. It's the most idiomatic chezmoi approach -- `.chezmoidata/` already
   defines profile/package configuration.
2. It doesn't fight omarchy -- on Linux, omarchy still does runtime
   switching for desktop apps.
3. The "gap" (tmux/zellij not switching with omarchy) is already the status
   quo and rarely matters in practice -- most people pick a theme and keep
   it.
4. If the gap bothers you later, Option C (hook bridge) is an incremental
   addition on top.
5. On macOS, it gives you themed terminals for free.

The theme data file becomes the single answer to "what's my base theme?"
across the entire dotfiles repo.

### Why This Doesn't Require a Separate Application

Chezmoi's template engine already does what omarchy's sed engine does --
substituting color variables into config files:

| | Omarchy | Chezmoi |
|---|---|---|
| Engine | `sed` on `.tpl` files | Go templates on `.tmpl` files |
| Variables | `{{ accent }}` from `colors.toml` | `{{ .theme.colors.accent }}` from `theme.yaml` |
| When | Runtime (`omarchy-theme-set`) | Build-time (`chezmoi apply`) |
| Scope | Linux desktop apps | Cross-platform terminal tools |

They're complementary, not competing. Omarchy handles apps that benefit
from live switching (desktop environment, editor, browser). Chezmoi handles
apps that don't need live switching (tmux, zellij -- you restart these
rarely).

## Part 4: Implementation Phases

### Phase 1: Add Missing Configs (No Theming Changes)

Add Hyprland, terminal, and desktop configs to chezmoi as-is. Platform-gated
via `.chezmoiignore.tmpl`. Terminal configs on Linux use omarchy imports
where applicable. No changes to existing tmux/zellij configs.

**Scope:**
- All files listed in Part 2
- `.chezmoiignore.tmpl` platform exclusion rules
- `run_onchange_00-setup-directories.sh` additions for new dirs

### Phase 2: Theme Data Layer

Create `.chezmoidata/theme.yaml` with Catppuccin Mocha definition. Refactor
existing configs (tmux, zellij) to reference `{{ .theme.* }}` instead of
hardcoded values. Add conditional color rendering for terminal configs on
macOS.

**Scope:**
- New `.chezmoidata/theme.yaml`
- Refactor `dot_config/tmux/tmux.conf.tmpl` to use theme vars
- Refactor `dot_config/zellij/config.kdl.tmpl` to use theme vars
- Terminal config templates (ghostty, kitty, alacritty) render theme colors
  on macOS, import omarchy on Linux

### Phase 3: (Optional) Hook Bridge

If switching themes feels incomplete, add an omarchy `theme-set` hook to
update `theme.yaml` and run `chezmoi apply` for tmux/zellij.

**Scope:**
- `dot_config/omarchy/hooks/theme-set` script
- Theme name mapping logic (omarchy name -> chezmoi theme values)

## Appendix: Omarchy Theme Architecture Reference

### Theme Definition Structure

Each theme lives in `~/.local/share/omarchy/themes/<name>/` (built-in) or
`~/.config/omarchy/themes/<name>/` (user-installed):

| File | Purpose | Required |
|---|---|---|
| `colors.toml` | 23 color variables (accent, bg, fg, cursor, selection, color0-15) | Yes |
| `backgrounds/` | Wallpaper images (cycled through) | Yes |
| `preview.png` | Theme preview for the picker UI | Yes |
| `icons.theme` | GNOME icon theme name (e.g., "Yaru-purple") | Yes |
| `neovim.lua` | LazyVim colorscheme plugin spec | Yes |
| `vscode.json` | VS Code theme name + extension ID | Yes |
| `btop.theme` | Static btop theme (overrides template) | Optional |
| `light.mode` | Marker: if present, sets GNOME to prefer-light | Optional |
| `waybar.css` | Static waybar CSS override | Optional |
| `hyprland.conf` | Static Hyprland config override | Optional |

### Template Engine Flow

```
colors.toml -> sed substitution -> rendered config files
                                   in ~/.config/omarchy/current/theme/

For each variable in colors.toml (e.g., accent = "#89b4fa"):
  {{ accent }}       -> #89b4fa       (raw hex)
  {{ accent_strip }} -> 89b4fa        (without #)
  {{ accent_rgb }}   -> 137,180,250   (decimal RGB)

Template sources (priority order):
  1. ~/.config/omarchy/themed/*.tpl   (user overrides)
  2. ~/.local/share/omarchy/default/themed/*.tpl  (built-in)
```

### Theme Switch Flow (`omarchy-theme-set <name>`)

```
1. Resolve theme directory (user themes first, then built-in)
2. Create temp: ~/.config/omarchy/current/next-theme/
3. Copy static files from theme dir
4. Run template engine (colors.toml + .tpl -> rendered files)
5. Atomic swap: next-theme/ -> theme/
6. Write theme.name
7. Cycle wallpaper
8. Hot-reload running apps:
   - waybar, swayosd (restart)
   - alacritty (touch config), kitty (SIGUSR1), ghostty (SIGUSR2)
   - hyprland (hyprctl reload)
   - btop, opencode (restart)
   - mako (makoctl reload)
9. Update app-specific themes:
   - GNOME dark/light + icon theme
   - Chromium/Brave titlebar color
   - VS Code/Codium/Cursor colorTheme
   - Obsidian vault themes
10. Fire hook: ~/.config/omarchy/hooks/theme-set
```

## Appendix B: Terminal Image Preview in Multiplexers

> Investigated 2026-02-28. Analysis of why image preview works in some
> multiplexer/app combinations but not others.

### Environment

| Component | Version |
|---|---|
| Outer terminal | Ghostty 1.2.3 (`TERM_PROGRAM=ghostty`) |
| tmux | 3.6a |
| zellij | 0.43.1 |
| yazi | 26.1.22 |
| superfile (spf) | 1.5.0 |

### Compatibility Matrix

| | Direct terminal | tmux | zellij |
|---|---|---|---|
| **yazi** | Works | Works | Broken |
| **superfile** | Works | Broken | Broken |

### How Each Tool Detects Kitty Graphics Protocol

**yazi** (Rust): Auto-detects via multiple methods:
1. Checks `$TERM`, `$TERM_PROGRAM` for known terminals
2. Detects `$TMUX` and `$ZELLIJ_SESSION_NAME` multiplexer env vars
3. Sends KGP query (`\e_Gi=31,s=1,v=1,a=q,t=d,f=24;AAAA\e\`) and
   checks response
4. Under tmux: wraps all KGP sequences in DCS passthrough
   (`\ePtmux;\e_G...\e\\\e\\`)
5. Under zellij: sends raw KGP sequences (zellij handles natively)

**superfile** (Go, `github.com/BourgeoisBear/rasterm` library): Env-only
detection at `rasterm/kitty.go`:
```go
func IsKittyCapable() bool {
    V := GetEnvIdentifiers()
    return (len(V["KITTY_WINDOW_ID"]) > 0) ||
           (V["TERM_PROGRAM"] == "wezterm") ||
           (V["TERM_PROGRAM"] == "ghostty")
}
```
No multiplexer awareness. No DCS passthrough wrapping. Sends raw APC
sequences (`\e_G...\e\\`).

### Root Cause Analysis

**tmux + superfile (BROKEN -- upstream limitation)**:
1. tmux does NOT propagate `TERM_PROGRAM` by default (not in
   `update-environment`). So `IsKittyCapable()` returns false.
2. Even if detection succeeded (fixed by adding `TERM_PROGRAM` to
   `update-environment`), rasterm sends raw APC sequences.
3. tmux only forwards sequences wrapped in DCS passthrough format
   (`\ePtmux;...\e\\`), per `man tmux`: "Allow programs in the pane to
   bypass tmux using a terminal escape sequence (\ePtmux;...\e\\)."
4. Raw APC sequences are silently absorbed by tmux.
5. **No config fix.** Requires upstream rasterm library change to implement
   tmux DCS passthrough wrapping.

**tmux + yazi (WORKS)**: yazi detects `$TMUX`, wraps all KGP sequences
in DCS passthrough format. `allow-passthrough on` is set in tmux config.
Outer Ghostty terminal processes the unwrapped KGP commands.

**zellij + superfile (BROKEN -- needs investigation)**:
1. Zellij preserves parent environment, so `TERM_PROGRAM=ghostty` should
   be available. `IsKittyCapable()` should return true.
2. Zellij 0.41+ natively handles KGP sequences (no DCS wrapping needed).
3. If detection works and KGP is native, the issue is likely:
   - Cell size detection failure (superfile's `detectTerminalCellSize`
     uses CSI 16t which zellij may not support)
   - A rendering path issue in rasterm's chunked image encoding under
     zellij's PTY handling
4. **Needs testing:** Run `echo $TERM_PROGRAM` inside zellij to confirm
   env preservation. If empty, the fix is setting it in fish config.

**zellij + yazi (BROKEN -- likely upstream)**:
1. Yazi detects `$ZELLIJ_SESSION_NAME` and should attempt KGP through
   zellij's native support.
2. Likely cause: zellij's KGP implementation has compatibility issues
   with yazi's specific usage (e.g., virtual placement, unicode
   placeholders, or chunked transfer).
3. Cell size detection via CSI 16t may also fail under zellij.
4. **Upstream issue in zellij or yazi.** Check
   [zellij#3789](https://github.com/zellij-org/zellij/issues/3789) and
   [yazi issues](https://github.com/sxyazi/yazi/issues) for status.

### Fixes Applied

**tmux config** (`tmux.conf.tmpl`):
```
# Propagate terminal identity for graphics protocol detection
set -ga update-environment "TERM_PROGRAM"
set -ga update-environment "TERM_PROGRAM_VERSION"
```
This ensures `TERM_PROGRAM=ghostty` is available inside tmux sessions,
fixing detection for tools that check it. Note: requires detach/reattach
for existing sessions. Does NOT fix the DCS wrapping issue in rasterm.

### Upstream Issues to Track

| Tool | Issue | Status |
|---|---|---|
| superfile/rasterm | No tmux DCS passthrough wrapping for KGP | Needs upstream PR to `BourgeoisBear/rasterm` |
| superfile/rasterm | No multiplexer detection (TMUX/ZELLIJ) | Needs upstream PR |
| zellij | KGP implementation may not support all features | Check zellij issues |
| yazi | Zellij KGP adapter may have compatibility issues | Check yazi issues |

### Workarounds

- **Under tmux**: Use yazi instead of superfile for image preview.
- **Under zellij**: No workaround for inline images currently. Use a
  non-multiplexed terminal for file browsing with images, or use
  `chafa`/`timg` for individual files (they may have their own
  multiplexer support).
